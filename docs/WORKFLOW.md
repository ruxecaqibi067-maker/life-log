# 主管对话与实现对话的协作方法

本项目按用户要求采用「一个主管对话＋若干实现对话」。主管维护范围、依赖、进度和验收，实现对话完成各自任务；不依赖用户复制整段聊天来传递状态。

## 1. 模型能力与任务粒度的估算依据

用户称为 ChatGPT-6.1 的模型，在本规划中以官方型号 **GPT-6.1 Sol** 作为能力参考。查阅日期为2026-10-22；实际对话选用的模型以客户端显示为准。

OpenAI 官方 API 模型目录列出 `gpt-6.1-sol` 的上下文窗口为1.05M tokens、最大输出128K tokens。这是 API 型号参数，不能据此保证用户的 ChatGPT/Codex 客户端、账号、某个对话拥有相同额度，也不代表接近上限时仍能稳定完成任意规模工程。[官方模型目录](https://developers.openai.com/api/docs/models)

本项目预期这种能力足以在一段对话内完成**边界明确、资料齐全、可运行检查的完整功能闭环**，包括读相关代码、实现、测试、修复和交接。环境安装、设备连接、系统权限或真实手机操作仍有外部条件。以下工作量是本项目的工程调度估计，不是模型基准测试、官方承诺或当前对话实际剩余窗口。

| 级别 | 合理任务形态 | 计划工作材料体量 | 对话安排 |
| --- | --- | --- | --- |
| S | 已有接口上的简单页面/设置接入 | 约10–25k tokens | 通常1个对话，可与另一个已就绪S任务顺序完成 |
| M | 一个中等模块的实现、测试与接入 | 约20–45k tokens | 通常1个对话完成1包 |
| L | 涉及系统文件、数据事务或复杂状态的闭环 | 约35–70k tokens；故障多时可能更高 | 默认1个对话1包，预留调试空间 |

“工作材料体量”粗略包括必要文档、代码片段、工具输出、讨论和交接；不是计费token，也不是承诺会精确落在此范围。长日志、重复读取、依赖下载失败会改变实际占用。T01–T03完成后，主管依据真实改动与调试负担重新评估后续任务。

16个任务包是可审查的拆分，**不等于必须开启16个对话**。简单且依赖已满足的任务可以在同一对话依次完成，但保留各自提交和交接；不要为减少对话数把恢复引擎、照片处理或真机验收糅在一个任务里。

拆分依据是结果边界：一个明确行为、一组稳定接口、可以独立验证、失败容易定位。理论上下文很大并不意味着应把整个第一版塞进同一个实现对话。官方长期任务经验也强调通过仓库、测试反馈与外化状态保持连续性。[长期任务实践](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)

## 2. 主管与实现的职责

| 角色 | 负责内容 |
| --- | --- |
| 当前主管对话 | 维护需求与技术基线；分派下一包；核对提交、测试和依赖；汇总STATUS；处理跨任务冲突；最终验收 |
| 实现对话 | 阅读本包及相关文件；实现与测试；修复本包问题；提交代码和独立交接；明确未执行项 |
| 用户本人 | 决定产品偏好；在自己的手机完成必要安装/授权/操作；提供实际使用反馈；保管正式签名资料 |

主管不会仅凭实现对话说“完成”就把功能算作验收通过。实现对话不要擅自修改中央进度板，避免多个对话覆盖状态。

## 3. 启动一个实现对话

1. 从 [STATUS.md](STATUS.md) 确认前置任务已接受，选择 [TASKS.md](TASKS.md) 中的下一包。
2. 让新对话工作在项目目录 `C:\Users\user1\Desktop\workspace\NEW TRY\life-log-android`。
3. 复制该任务文件开头的提示词；它应先读AGENTS、本包、相关需求技术章节与直接前置交接。
4. 实现对话检查Git状态和前置提交，建立任务分支，按完成条件推进。
5. 完成后把简短交接摘要交回主管；完整信息已在 `docs/handoffs/Txx.md`，无需复制所有日志。

推荐的通用提示词（替换Txx）：

```text
请在 C:\Users\user1\Desktop\workspace\NEW TRY\life-log-android 执行 Txx。
先读 AGENTS.md、docs/WORKFLOW.md、docs/tasks/Txx.md 与其中列出的直接前置交接。
核对实际代码和Git状态，然后实现本任务，运行对应检查并修复问题。
当前对话负责实现，不扩展第一版范围；中央STATUS由主管维护。
将代码与 docs/handoffs/Txx.md 一起提交，回报分支、提交、检查结果、未验证项及下一任务所需信息。
不存在的工具、没有执行的检查和未连接的真机项目不能写成通过。
```

对话无需自动继承主管历史；仓库文件才是可重复读取的上下文。清晰目标、相关上下文、约束与完成条件也符合 [OpenAI 官方实践](https://learn.chatgpt.com/docs/learn/best-practices)。

## 4. Git流程：默认串行

同一个工作目录同时只允许一个实现对话写入。推荐顺序为T01至T16，避免不同对话同时切分支和修改导航/数据库。

开始任务时：

```powershell
git status --short
git branch --show-current
git log -5 --oneline
# 确认没有他人未提交修改，前置已合入main后：
git switch main
git switch -c task/t01-bootstrap  # 示例，其他任务使用自己的编号与名称
```

发现本任务已有分支时先检查并继续，不重复新建；发现不属于本任务的未提交修改时先查清来源，不强制清理。不要修改用户全局Git配置。

实现交付时：

- 运行本包相关检查，记录真实输出及失败/未执行原因。
- 逐文件暂存本包内容、必要schema和本包handoff；先检查diff，避免带入私有数据。
- 提交为一个或若干有意义的commit，回报最终HEAD；handoff里记录实现提交，最终HEAD在摘要中补充即可，避免自引用commit循环。
- 不擅自将其他任务合入、不强推、不删除分支和不清理他人文件。

主管验收后将任务分支合入main，复核必要集成检查并更新STATUS。下一个任务从更新后的main开始。当前主管已经创建的仅为文档基线，不表示任何实现任务完成。

## 5. 可选并行：不是默认操作

T02数据契约接受后，部分功能有并行空间，例如照片服务与界面壳；界面壳完成后，饮食、作息、项目管理也可按文件边界并行。

只有满足以下条件才安排并行：

- 前置交付已提交并合入共同基线；不是边猜接口边开发。
- 每个对话使用独立分支和独立worktree；不能共享一个正在被写入的工作目录。
- 共享的 `AppContainer`、导航、Manifest、依赖、Room schema 有明确集成顺序；冲突由主管协调，不能各自重写。
- 每个任务完整交接，主管逐个合并并复测，不同时做无法归因的大合并。

暂不建立worktree或新用户对话。用户开始具体任务后再按需要安排；源码主仓库仍是当前独立Git目录。

## 6. 上下文变长时怎样继续

不以“聊了多少轮”判断是否换对话，也不把普通测试失败当作必须换对话的理由。出现以下情况时先落盘检查点，再决定是否拆分或新开对话：

- 新增工作已经形成第二个独立功能，明显超出本包完成条件。
- 大量输出已挤占当前任务信息，模型开始重复探索或混淆决定。
- 修复涉及未知工具链、系统相机、厂商行为等独立问题，值得提取为缺陷任务。
- 客户端提示窗口压力，或自动压缩后仍缺失关键状态。

检查点必须包含：分支/提交、已改文件、已通过检查、当前失败的精确复现、未提交改动、下一条具体动作。新对话从这些文件与代码继续，不从头重做，不靠换对话掩盖未解决问题。

## 7. 交接与主管接受

实现对话填写 [交接模板](handoffs/TEMPLATE.md)，各自保存 `docs/handoffs/Txx.md`。最少要有：

1. 范围与实际行为；分支、实现提交、最终HEAD。
2. 修改文件和共享契约变化；schema/格式版本影响。
3. 执行的命令、结果、日志/截图路径；没有执行的检查与原因。
4. 数据可靠性、照片、备份等相关用例结果；真实设备与模拟器结果分开。
5. 已知问题、外部条件、下一任务可依赖的接口和入口。

主管依次核对：范围、diff、测试证据、可访问入口、对下游的影响。必要时退回原实现对话修复；只在确有独立边界时再拆缺陷包。

实现代码可接受但手机证据尚缺时，记录为“实现已接受，真机待验证”；不能据此宣布v0.1可日常使用。最终门槛见 [ACCEPTANCE.md](ACCEPTANCE.md)。

## 8. 本轮交付与下一步

本轮只建立独立Git、需求、技术路线、验收标准、任务包和交接框架，不安装Android工具、不生成App代码、不创建用户对话。

下一步由用户在另一个对话执行 [T01](tasks/T01.md)。回报环境与空工程提交后，主管核对并启动T02。
