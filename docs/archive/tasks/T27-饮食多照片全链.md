# T27 同一餐多照片全链

对应反馈7，前置已发布0.1.6/code9，Room/备份v6。读取[反馈与分工](FEEDBACK-2026-10-26-第二轮界面与饮食照片.md)，独立实现数据→媒体→编辑/详情→备份/恢复完整闭环。

## 用户操作

- 同一条饮食记录连续拍照或从相册追加照片，不覆盖已有照片；缩略图列表、数量、逐张预览/删除，详情可浏览所有照片。首张作为首页/回顾封面并提示总张数，仍只有一条饮食记录。
- 保持只写文字、只拍照片都能保存；标题、饱腹感、日期/钟点和草稿不受影响。首版最多9张，明确显示上限及错误，不静默丢照片；有余量可多次继续添加，不要求新权限。
- 编辑取消或删除未保存照片不提前破坏已保存文件；拍照/选图取消保留已有列表，恢复草稿保留稳定ticket ID集合，不持久化临时URI。部分图片失败不吞掉已准备好的其他照片，保存失败保留可重试草稿。

## 数据与媒体安全

- 新建有顺序的MealPhoto关联表，显式Room6→7迁移；每个旧photoId转成首张，不丢照片或文字。保留MealRecord.photoId为首张兼容字段及旧单照片调用（不能让旧调用编辑文字时误删其他照片）；新列表为权威关联，封面与顺序一致。
- 保存新/旧多图在同一写协调/Room事务中提交关联与媒体；照片必须落应用files。失败/取消不能留下部分业务记录或删除原文件，暂存可恢复/清理；引用计数、孤儿清理、删除整餐、进程重开涵盖所有关联，不能只检查photoId封面。
- 保存接口在`docs/handoffs/T27-CONTRACT.md`先给最小稳定合同，向主管及T25说明兼容边界。保持现有API尽可能兼容，仅按真实需要新增方法/参数，不新增重型架构或依赖。
- 新导出备份v7，旧v1–v6读取构建一张/无照片关联；快照、计数、严格校验、资源上限、ZIP照片自检、预览/完整恢复/提交前失败/取消与回滚均含所有照片及顺序，不只改UI。旧schema1–6保留，备份工具增加显式旧→7语义比较，旧版本App拒绝新格式。
