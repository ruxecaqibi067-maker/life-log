## 实际交付与文件

- `data/media/PhotoIntents.kt`：`PickMealPhoto` 单图片合约；系统 Photo Picker 可用则使用，不可用明确回退 `ACTION_OPEN_DOCUMENT` / `image/*` / OPENABLE。没有 Play Services 补装配置。`TakeMealPhoto` 继承 TakePicture，补 ClipData 与临时读写 URI 授权。
- `PhotoNormalizer.kt`：实际流式输入上限 100MiB，真实解码器校验签名/头与可解码性；头部像素上限 100MP；在像素分配前指定最长边 2048 的目标尺寸，按比例缩放、不放大小图。API28+ `ImageDecoder` 应用 EXIF 旋转/镜像，拒绝部分损坏图，软件解码到 sRGB；透明区铺白，重新编码 JPEG 质量85，不带原图 EXIF/GPS。正式输出上限 8MiB，检查输出 JPEG 尺寸、字节数并计算 SHA-256。
- `PhotoFiles.kt` / `PhotoModels.kt`：受控路径、AtomicFile 持久票据和明确错误/取消结果。所有目录由本机规范 UUID 生成，拒绝路径越界和符号链接歧义，不使用外部 URI/JSON 提供的文件路径；清理只删除已知文件，不递归遍历未知目录。
- `PhotoStorage.kt`：全部阻塞处理在 `Dispatchers.IO`；同一个 `WriteCoordinator` 保护处理、文件就位、DB 引用提交、回收。内部 Mutex 还保护继承同一写租约的兄弟协程，避免 release 在 save 验证文件后、提交前回收文件。Room 仍是正式记录/引用的唯一来源，票据只描述未保存媒体工作。
- `AppContainer.photos` 惰性装配同一个数据库、记录 Repository、写协调器和 Clock。没有修改 RecordRepository 的既有契约。
- Manifest 新增 `${applicationId}.photos` FileProvider，`exported=false` / `grantUriPermissions=true`；`photo_paths.xml` **只暴露 `files/photo-capture/`**。正式媒体、数据库、整个 files 和 cache 均不在暴露根中；没有新增 CAMERA、整库相册、联网、定位或通知权限。
- 主机测试：`PhotoNormalizerTest` 8、`PhotoIntentsTest` 3、`PhotoStorageTest` 21；设备测试 `PhotoDeviceTest` 3。测试图全部由代码生成，没有照片、设备序列号、备份或真实生活数据入 Git。

实现依据核对过 [Photo Picker 官方说明](https://developer.android.com/training/data-storage/shared/photo-picker) 与 [ImageDecoder API](https://developer.android.com/reference/android/graphics/ImageDecoder)。沿用 minSdk28，不引入额外图片运行库。

## 目录、状态与提交协议

所有路径相对应用私有 `filesDir`，正式文件不在 cache：

| 状态 | 文件/来源 | 规则 |
| --- | --- | --- |
| 待处理 | `photo-staging/<ticketId>/state.json`，相册输入 `source`；相机输出 `photo-capture/<ticketId>.jpg` | AtomicFile 写入版本1的本地票据；相册结果立即按实际流读取复制，不长期持有相册 URI；来源可被删除/撤权 |
| 已处理、待保存 | 同票据，含 MediaAsset 元数据；`photo-staging/<ticketId>/normalized.jpg` | 尚无饮食/MediaAsset DB 行；可预览、恢复票据、撤销；此时不是业务保存成功 |
| 正式文件就位、待引用 | `media/<generationId>/<photoId>.jpg`，票据仍在；`photoId=ticketId` | 校验规范图后同文件系统 rename；已有目标仅允许哈希/大小完全吻合的重试，绝不覆盖。重新验证并 fsync 正式目录及父目录，再调用 Repository |
| 已引用 | Room MediaAsset + MealRecord.photoId，同一个 SQL 事务提交 | 只有到此才返回保存成功；旧图在提交后再回收，不能先删旧图。正式媒体 metadata/path 仍遵循 T02，不修改 schema |

- 每个新图生成独立 generation UUID，不持久化“当前 generation”全局偏好；恢复可使用自己的新 generation。DB 相对路径始终为 `media/<generationId>/<photoId>.jpg`。未来备份 ZIP 的 `media/<photoId>.jpg` 是另一种路径，不混用。
- DB 失败时新正式文件和票据保留以供重试，旧引用完全不变；调用 `release` 取消后回收无引用新图。进程在移动前/后被终止，票据可重新定位到规范图或正式图；提交后被终止，Room 引用决定保留新图，后续 maintain 只回收旧图。
- 相册复制/处理异常和协程取消尽力立即移除该导入票据/输入，取消异常继续传播，不伪装成功。相机取消立即撤销授权并删除本票据/拍摄文件，不写记录；相机“成功”但空文件/坏图仍返回错误，保留相机票据供重试或显式 release。
- `maintain(retainedTickets)` 先续期传入票据，再清理。没有显式保留的票据最后使用超过 **7天**才视为遗弃；短暂重建不清理活动相机 URI。票据和其规范/待引用正式文件在宽限期内受保护；**所有有效 Room 引用不受票据是否存在/过期影响**。无票据的拍摄遗留也按7天回收。
- GC 在共享写保护内先删除未引用且无活动票据保护的 DB 媒体行，再根据保留 DB 行/票据集合清理已知媒体文件；只删空 generation 目录。清理失败可留孤立文件重试，不能删除仍有有效引用的文件。共享照片直到最后一餐解除引用才删除。
- 提交之后的清理异常只延期，不把已提交保存误报为失败。后续页面恢复/启动调用 maintain 补清理；没有在本包给 T03 主界面偷偷添加生命周期任务。

## 公共接口与 T05 接入

通过 `(application as App).container.photos` 使用，UI/ViewModel 不操作 DAO 或文件。返回 `PhotoResult.Success(value)` / `Failure(error, dataError?)` / `Cancelled`；协程取消抛出 CancellationException。数据库/业务输入失败保留原有 DataError，例如 EMPTY_MEAL、TEXT_TOO_LONG；页面优先解释 dataError，再解释媒体错误，不能直接显示堆栈。

| API | 接入用途 |
| --- | --- |
| `beginCapture()` → CaptureRequest | 在后台准备票据和临时 URI；将 `ticket.id` 先存 SavedStateHandle，再 `TakeMealPhoto` launcher.launch(uri) |
| `resumeCapture(ticket)` | 页面/进程重建时复原同一个 URI；不要重新创建票据或再次自动启动相机。使用稳定 ActivityResult 注册键接收已有返回 |
| `finishCapture(ticket, succeeded)` | 相机回调使用已存票据；false 是取消，不生成记录；成功仍需要实际处理图像 |
| `importPhoto(uri?)` | `PickMealPhoto` 回调立即交服务复制/处理；null 返回 Cancelled。失败保留页面文字输入，允许继续纯文字记录 |
| `resumePrepared(ticket)` / `previewUri(ticket)` | 从已存 ID 验证并恢复待保存图、取得仅供应用内部图片加载的 file URI；不依赖原相册 URI |
| `saveMeal(draft, ticket?)` | 新图票据控制新的 photoId；无票据时按 draft.photoId 保留/移除已有图。先就位文件再组合 records.saveMeal。返回成功后才提示已保存 |
| `deleteMeal(id)` | 先删记录后回收照片；有图片的饮食编辑/删除走此服务，避免页面绕过文件一致性层 |
| `release(ticket)` | 显式取消/移除待保存图，或保存成功后释放票据；已被 Room 引用的正式文件保留。失败可重试，也可交 maintain |
| `maintain(retainedTickets)` | 页面启动/恢复时提供 SavedStateHandle 中全部活动票据；先恢复或丢弃 INVALID_TICKET 的失效草稿 ID，再重试 maintain。异常显示错误，不能当成空记录 |
| `photoUri(photoId)` | 读取已保存图片并校验哈希/大小；内部加载使用，不能把 file URI 发给外部应用 |

典型次序：选择/拍摄 → 显示处理中 → 保存 PreparedPhoto.ticket.id → 预览 → `photos.saveMeal(draft, ticket)` → Success 后 `photos.release(ticket)` 并清空草稿票据。release 失败不能撤销已成功的保存；在稍后 maintain 重试。保存失败不要丢掉文字、记录 ID 或票据，重试沿用同一 ID。拍照 launcher 无处理 Activity/启动异常时 release 已创建票据并提示换用相册/文字，页面负责 Activity 启动异常展示。

只需要纯文字保存也可用 `photos.saveMeal(draft)`，仍由 T02 校验文字/照片至少一个。所有文件操作为 suspend，页面显示处理中/保存中并防重复操作；本包没有完整页面，也没有未经测量的性能达标声明。

## T11/T13 保护契约

- T11 沿用 `container.writes.withExclusiveAccess`，从一致 snapshot 取引用并复制照片，持锁直到照片拷贝结束，不能只拿到路径后提前放锁。不要在同一继承租约里同时运行业务写入/导出；该租约用于顺序组合多个操作。
- 为避免尚未引用的恢复 generation 被普通 GC 删除，预留私有 **`files/media-recovery.pending`** 屏障。T13 必须在共享排他锁内、准备恢复 generation **之前**持久写屏障；启动时先检查恢复日志与 `RestoreState.lastCommittedRestoreId`，完成新旧引用及文件对账后才删除屏障。屏障存在期间本服务拒绝媒体读写/清理，返回 RECOVERY_REQUIRED，绝不自行清除。
- 本包仅实现门禁协议和测试；没有实现恢复日志、替换事务、自动回滚或启动恢复引擎，不能据此宣称 T13 中断恢复可用。若 T13 使用不同日志位置，必须显式接通此屏障或替换统一门禁，不能绕过。
- Room v1 identityHash 仍为 `ec52ae9557beb8e2372e3ed687205fcc`；没有 schema/迁移/备份格式变更。共享改动仅 AppContainer 的 import + `photos` 装配，以及 FileProvider Manifest；和 T03 合并时保留双方新增装配/入口，不覆盖整个文件。
