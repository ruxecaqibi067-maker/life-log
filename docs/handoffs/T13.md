## 接口与提交点

- `AppContainer.restoreEngine.restore(StagingToken)` 接受 T12 的进程内有效 token；执行前重新校验 ZIP 和全部照片。所有工作持有共享 WriteCoordinator，预检/取消使用 importer Mutex，不存在先清库再补文件的路径。
- 恢复结果：`FailedBeforeCommit(error)`、`Committed(restoreId)`、`CommittedCleanupPending(restoreId)`；额外 `RecoveryRequired(error)` 表示无法读取提交标记，保留现场并阻止写入。取消在提交前抛出且原数据不变；提交后引擎按标记保留新状态，UI 必须重新查询状态，不能把取消通知解释为自动回滚。
- 状态机：`PREPARING_ROLLBACK → ROLLBACK_READY → PREPARING_MEDIA → MEDIA_READY → DATABASE_COMMITTED → 清理`。唯一提交点是 Room 单事务同时替换全部业务表/设置并写 `lastCommittedRestoreId`；日志 phase 只用于诊断，启动始终以数据库标记判断旧/新状态。
- `media-recovery.pending` 是 AtomicFile 持久化日志兼 T04 屏障，包含 restoreId、新 generation、旧 generation 列表、stagingId、阶段。先写日志并 fsync 目录，再准备照片；每张新图 FileDescriptor.sync 并复核哈希/解码，再同步 generation/media/filesDir，最后进入 DB 事务。
- 提交前旧行/旧图保留；异常清理新无引用 generation。提交后只清理旧无引用 generation，清理失败返回已提交/待重试，不恢复半套旧图。清理检查当前 MediaAsset 引用，重复执行幂等。

## 回滚与启动

- 开始前按旧照片、JSON、回滚工作副本、自检及新照片估算峰值，另留 32 MiB 余量。空间检查失败立即停止；运行中真实 I/O/ENOSPC 仍由异常路径处理。估算不保证其他应用不会同时占用空间。
- 回滚保存在非 cache 私有 `backup-rollback/<restoreId>.zip`，重新完整预检后才 AtomicFile 发布 `latest.json`，再删除旧回滚。最新完整包保留，不含绝对路径或密钥；卸载会丢失。
- `preflightRollback()` 返回普通 T12 预检，仍由用户确认再调用 restore；`exportRollback(BackupDestination)` 可通过 SAF 保存完整回滚包，写入前再验证，不绕过完整恢复协议。
- `App.onCreate` 在 IO 协程启动恢复；`AppContainer.writes` 的 beforeWrite 在每次正式写入前再次协调，尚有日志时先验证当前有效照片并完成清理，失败时保留屏障。T04 原有屏障检查继续有效。启动清理遗弃导出/导入暂存和非最新回滚工作文件；同进程有效 token 保留。
- 恢复成功会让现存编辑草稿引用失效；T14 应退出编辑、刷新 Room 状态，重新选包后重试失败的恢复，不持久化 token 或缓存解码后的 DataSnapshot。
